# 원치 않은 입금 소명 지원 도구

모르는 주소에서 들어온 입금 1건을 조사해서, 거래소에 낼 자료로 정리하는 도구입니다.

자료는 네 가지를 나눠서 담습니다.

- 온체인에서 확인되는 것
- 분석한 정황
- 사용자 설명
- 확인할 수 없는 것

결백을 판단하거나 위험 점수를 매기지 않습니다.

## 이 도구로 답하려는 질문

**온체인 기록은 "원치 않은 입금"이라는 걸 어디까지 설명할 수 있는가?**

| | 내용 |
|---|---|
| 문제 제기 | 위험 주소에서 돈을 받았다는 사실만으로 받은 지갑을 위험하다고 봐도 되는가? |
| 가설 | 의도나 결백은 증명할 수 없다. 대신 이전 관계 없음, 여러 주소에 비슷한 금액 뿌리기, 입금 이후 기록 같은 확인 가능한 정황은 보여줄 수 있다. |
| 진행 | 실제 사례를 이 도구에 넣는다 → 결과 표가 질문의 답과 한계가 된다 → 같은 결과를 소명 자료로 내보낸다 |

## 화면 흐름

| 단계 | 하는 일 |
|---|---|
| 1. 입금 찾기 | 지갑 주소로 찾기(메타마스크 주소 불러오기 가능) 또는 거래소 입금 목록에서 찾기 |
| 2. 온체인 조사 | 아래 A~E 분석과 제재 목록 조회. 결과는 사용자가 고칠 수 없음 |
| 3. 내 설명 | 질문 3개, 날짜, 설명, 첨부. 모든 답은 "선택 안 함"으로 시작 |
| 4. 자료 생성 | 네 가지로 나눈 보고서. PDF 저장(브라우저 인쇄) |

## 조사 항목

| 코드 | 무엇을 보나 | 결과 구분 |
|---|---|---|
| A | 거래 자체: 언제, 누가, 얼마 | 확인된 기록 |
| B | 입금 전 두 주소 사이 직접 거래 | 확인된 기록 |
| C | 보낸 주소가 입금 전후 24시간 동안 비슷한 금액(±10%)을 보낸 주소 수 | 분석한 정황 |
| D | 입금 후 보낸 주소로 다시 보냈는지, 처음 나간 전송은 언제 | 확인된 기록 (순서만) |
| E | 의도, 온체인 밖 관계, 받은 돈을 썼는지, 조회 범위 밖 | 확인할 수 없음 |
| S | 보낸 주소가 제재 목록과 일치하는지 | 확인된 기록 |

조사 기간은 "지금"이 아니라 **입금 시각** 기준입니다.

## 보고서 구성

| 구분 | 예시 | 사용자가 뺄 수 있나 |
|---|---|---|
| 확인된 기록 | 보낸 주소와 이전 직접 거래 0건 | 못 뺌 |
| 분석한 정황 | 입금 전후 24시간 동안 보낸 주소가 34개 주소에 비슷한 금액을 보냄 | 못 뺌 |
| 사용자 설명 | 요청한 적 없다고 설명함. 답하지 않은 항목은 "미확인" | 사용자가 직접 씀 |
| 확인할 수 없음 | 사용자의 실제 의도, 온체인 밖 관계, 받은 돈을 썼는지 | 못 뺌 |

모든 항목에는 항상 두 가지가 붙습니다.

- **조사 범위:** 기간, 건수, 조회 시각, 데이터 출처, 실패한 범위
- **원본 링크:** 거래 해시, 이더스캔 링크

문장 규칙은 [docs/writing-rules.md](docs/writing-rules.md)에 있습니다.

## 외부 서비스

| 서비스 | 결정 |
|---|---|
| AMLBot 위험 점수 | 넣지 않음. 아티클 비교 자료로만 검토 |
| Blockpit | 연동하지 않음. 비교 대상으로 분석 |
| Chainalysis 무료 제재 조회 | 쓰지 않음 (2026-03-18 이후 업데이트 중단) |
| OFAC 공개 제재 목록 | 선택 기능. "조회한 목록에서 일치하지 않음"으로만 표시 |
| 업비트, 바이낸스 | 입금 목록 불러오기 (읽기 전용 키, 저장하지 않음) |
| 메타마스크 | 주소만 불러옴. 서명은 요청하지 않음 |

## 범위

| 하는 것 | 안 하는 것 |
|---|---|
| 이더리움 메인넷, ETH와 ERC-20 | 결백 판단, 위험 점수 |
| 입금 1건 조사, PDF 저장 | 서명 요청, 개인 키 요청 |
| 데모 모드 (고정 데이터) | 내 전체 자금 출처 추적 |
| 실제 조회 모드 | |

## 실행

```bash
npm install
cp .env.example .env.local   # 처음 한 번
npm run dev                  # http://localhost:3000
```

| 명령 | 하는 일 |
|---|---|
| `npm run dev` | 개발 서버 |
| `npm test` | 분석 함수 테스트 (고정 데이터, API 키 필요 없음) |
| `npm run typecheck` | 타입 검사 |
| `npm run build` | 배포용 빌드 |

### 모드

| `DATA_MODE` | 데이터 | 언제 |
|---|---|---|
| `demo` (기본값) | `src/fixtures/demo-case.ts` 고정 데이터 | 개발, 발표 |
| `live` | Alchemy, 거래소 API 실제 조회 | 연동 확인 |

데모 데이터의 주소와 거래 해시는 가짜라서 이더스캔 링크를 눌러도 결과가 없습니다. 화면 왼쪽에 "데모 데이터" 표시가 뜹니다.

## 구조

```text
src/
├── app/
│   ├── page.tsx                # 화면
│   └── api/                    # 서버 API (docs/api.md)
├── features/case/              # 4단계 화면
├── lib/
│   ├── api/cases.ts            # 화면 → 서버 호출은 여기서만
│   └── wallet.ts               # 메타마스크 주소 읽기
├── server/                     # 서버 전용 코드 (API 키는 여기서만)
│   ├── providers/              # 온체인 데이터 가져오기 (demo / alchemy)
│   ├── exchanges/              # 거래소 입금 목록 (업비트 / 바이낸스)
│   ├── sanctions/              # 제재 목록 조회
│   ├── analysis/               # A~E 분석 (순수 함수 + 테스트)
│   ├── report/                 # 보고서 문안
│   └── constants.ts            # 조사 기간·상한 같은 기준값
├── fixtures/demo-case.ts       # 데모 고정 데이터
└── types/case.ts               # 화면과 서버가 주고받는 데이터 모양
```

데이터는 한 방향으로 흐릅니다.

```text
providers / exchanges  →  Transfer[]  →  analysis (A~E, S)  →  CaseAnalysis  →  report  →  화면
```

각자 맡은 칸만 고치면 되도록 나눴습니다. 칸 사이의 약속은 `src/types/case.ts`입니다.

## 역할

| 역할 | 할 일 | 폴더 |
|---|---|---|
| 데이터 | Alchemy로 입금·전송 기록 가져오기, 페이지 넘기기와 상한, 실패 범위 기록, OFAC 목록 파일 만들기 | `src/server/providers/alchemy.ts`, `src/server/sanctions/` |
| 분석 | A~E 기준 다듬기, 문장 규칙 지키기, 경계 사례 테스트 | `src/server/analysis/` |
| 거래소 연결 | 업비트 입금 목록(바이낸스는 여유 있으면), 키 안내 문구, 1단계 화면 | `src/server/exchanges/`, `TransactionScreen.tsx` |
| 리포트·통합 | 보고서 문안, 화면 다듬기, PR 검토, 합치기 | `src/server/report/`, `src/features/case/` |
| 리서치팀 | 데모용 공개 사례 1건 (보낸 주소, 기간) | `src/fixtures/demo-case.ts` |

각 파일 맨 위에 `TODO(역할)`로 할 일을 적어뒀습니다. `grep -rn "TODO(" src`로 모아 볼 수 있습니다.
